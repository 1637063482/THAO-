## Findings

### High - Successful Quick Add permanently disables confirmation on the next open

- **Files/lines:** `src/js/quick-add.js:83-87,136-152`; `index.html:323`; `TASK_PLAN.md:222,226`.
- **Evidence:** On every submit, the code sets `submitButton.disabled = true` at lines 83-87. The success path closes the modal and resets only `submitInFlight` at line 152; it never assigns `disabled = false` or removes `aria-busy`. `openQuickAdd()` also does not restore that control. Consequently, after a successful record and reopening the sheet, the confirm button remains disabled. The R2 test suite covers only a re-entrant call during `triggerCloudSave()` and has no successful-submit/reopen assertion.
- **Impact:** The primary Quick Add button becomes unusable after the first successful record, breaking the normal repeated-entry workflow.

### Medium - Validation-return paths leave stale `aria-busy`

- **Files/lines:** `src/js/quick-add.js:86-108`.
- **Evidence:** Each early validation return re-enables the button but does not remove `aria-busy`, whereas the thrown-save path does remove it. Thus assistive technology can be told that the control remains busy after an invalid amount or unavailable FX rate.
- **Impact:** The accessible state diverges from the interactive state and can mislead keyboard/screen-reader users.

## Minimum Correction

1. Centralize submit-control reset and invoke it after success before the next open, after every validation/failure path, and in `openQuickAdd()`. Restore both `disabled=false` and removal of `aria-busy`.
2. Add tests that perform a successful submit, reopen the real sheet, and assert the confirm button is enabled and can submit again; also assert invalid VND and FX-validation paths clear `aria-busy`.
3. Preserve the existing R2 positive-safe-integer and single-write behavior while making this correction.
