## Findings

### High - Local edits and active-month changes still do not refresh the dashboard

- **Files/lines:** `src/js/main.js:82,175-180,329-340`; `src/js/render.js:11-31`; `src/js/dashboard.js:75-90`.
- **Evidence:** R3 defines wrappers only on `window.fullRebuildDOM` and `window.softUpdateDOM`. However `switchMonthTab()` calls the lexical imported `fullRebuildDOM()` directly, bypassing `window.fullRebuildDOM`. Local input debounce calls lexical `calculateAll()` directly and never calls `initDashboard()`. Thus only the remote listener's existing `window.softUpdateDOM()` route reaches the new wrapper. No test covers edit or month-switch refresh.
- **Impact:** The dashboard can display stale values after the normal local write path and after selecting a different month, contrary to the current-fact requirement.

### High - Visual evidence uses injected markup instead of the delivered dashboard renderer

- **Files/lines:** `docs/review-evidence/UXS-004.md:64-65,88-89`; `docs/review-evidence/assets/UXS-004/viewport-360.png`; `viewport-768.png`; `viewport-1920.png`; `TASK_PLAN.md:206,209-210`.
- **Evidence:** The evidence states that screenshots inject synthetic dashboard HTML because the authentication callback does not fire. I inspected the 360, 768, and 1920 images: they show that injected dashboard mockup, but cannot prove `initDashboard()`, `buildDashboardViewModel()`, localization, privacy classes, refresh behavior, or the actual DOM use the same rendering path.
- **Impact:** The six required captures do not validate the delivered UI at the required sizes. They are not sufficient proof of mobile-first behavior, long Vietnamese, privacy masking, or renderer/layout integration.

### Medium - Locale-file change remains outside the restored approved Task plan

- **Files/lines:** `TASK_PLAN.md:199`; `src/locales/vi.js`; `src/locales/zh-CN.js`; `docs/review-evidence/UXS-004.md:85-86`.
- **Evidence:** R3 restores the original Task plan, whose allowed files do not include the two locale modules, but leaves their dashboard-key changes in the implementation. The evidence acknowledges that a user-approved amendment is required, yet the state is submitted as `READY_FOR_REVIEW`.
- **Impact:** The change remains outside the authorized Task boundary. A known missing authorization cannot be waived by evidence text.

## Minimum Correction

1. Invoke `initDashboard()` from the real local-update and active-month paths in `src/js/main.js` (not only via `window` replacement), while retaining the remote snapshot refresh. Add tests proving an edit and `switchMonthTab()` update the rendered hero without resetting state or pending updates.
2. Capture all six sizes through the actual `initDashboard()`/`renderDashboard()` path with a synthetic legacy state. Do not inject handcrafted dashboard HTML. Record long Vietnamese, privacy-mask, overflow, mobile first-screen priority, and desktop layout observations.
3. Remove the locale-file changes or obtain an explicit user-approved Task-plan amendment before modifying those files. Do not return to `READY_FOR_REVIEW` while that authorization remains pending.
