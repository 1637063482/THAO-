## Findings

### High — `expectedInterestVnd` nullability conflicts between the UI contract and ADR schema

- **Files/lines:** `UI_SAVINGS_REDESIGN_PLAN.md:359-362`; `docs/adr/004-ui-savings-boundary.md:69-70,91`.
- **Evidence:** The UI contract states that an unset `expectedInterestVnd` is written as `null`. ADR-004 defines the same field as `VND integer`, without `| null`, while only `actualInterestVnd` is nullable.
- **Impact:** UXS-010/011 cannot implement a single converter/runtime schema: one compliant implementation must accept `null`, while the other must reject it. This is a direct conflict in the required storage contract.
- **Minimum correction:** Make the nullability identical in UI plan, ADR-004, and the schema listing. Either declare `expectedInterestVnd: VND integer | null` and specify the display fallback, or require a persisted integer and remove the `null` write path.

### Medium — R2 is marked ready while state and evidence still name the R1 implementation head

- **Files/lines:** `TASK_STATUS.md:14`; `docs/review-evidence/UXS-001.md:9,105`; actual rework commit `b03774b`.
- **Evidence:** `TASK_STATUS.md` sets `READY_FOR_REVIEW`/round 2 but retains `10194ed` as `Implementation Head`. Evidence also retains that SHA even though it records R1→R2 changes from `b03774b`.
- **Impact:** This violates `AGENT_WORKFLOW.md` §3.1/§5: Terra is required to review the state-recorded `base_sha..implementation_head`, and a rework review must identify the new head. The repository cannot prove which revision was submitted for R2.
- **Minimum correction:** During the documentation-only rework, update evidence and `TASK_STATUS.md` to the final new implementation SHA, retain the base SHA, set the correct review round/state transition, and return to `READY_FOR_REVIEW` only after that state commit.
