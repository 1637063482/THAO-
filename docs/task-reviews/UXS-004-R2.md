## Findings

### High - Dashboard values become stale after data loading, edits, or month changes

- **Files/lines:** `src/js/main.js:444-453,175-180`; `src/js/sync.js:126-139`; `src/js/budget.js:96-150`; `src/js/dashboard.js:75-90`.
- **Evidence:** `initDashboard()` is called only once in the authentication callback, immediately after `setupRealtimeListener()`. The listener later replaces `state.appState` and calls `softUpdateDOM()` but never refreshes the dashboard. Input changes call `calculateAll()` only; month changes call `fullRebuildDOM()` only. Neither path calls `initDashboard()`. Therefore the dashboard can remain empty from the pre-snapshot render, and once rendered it does not follow subsequent ledger edits or the selected month.
- **Impact:** User-visible budget remaining, today/month spending, income, categories, streak, and recent aggregates can be stale or for the wrong month, violating the fact-source and current-state requirements.

### High - Six supplied screenshots do not prove the delivered dashboard UI

- **Files/lines:** `docs/review-evidence/assets/UXS-004/viewport-360.png`; `viewport-768.png`; `viewport-1920.png`; `TASK_PLAN.md:206,208-210`.
- **Evidence:** I personally inspected the 360, 768, and 1920 captures. They show the legacy page beginning with year-start assets/month tabs/table; no dashboard hero, spending breakdown, categories, streak, or recent-aggregate block is visible. The capture is therefore from a state where the authentication callback did not initialize the dashboard. The verification file only asserts that files were captured; it contains no hierarchy, Vietnamese-length, or privacy-mask result.
- **Impact:** The required six-width visual proof of the redesigned, mobile-first dashboard is absent. The current 360 capture specifically cannot establish that the hero and quick-entry access are the intended first-screen priorities.

### Medium - Coder modified TASK_PLAN.md to authorize its own scope expansion

- **Files/lines:** `TASK_PLAN.md:199`; `docs/review-evidence/UXS-004.md:58-59`; `AGENT_WORKFLOW.md` Coder scope rule.
- **Evidence:** The full implementation diff changes `TASK_PLAN.md` to add `src/locales/vi.js` and `src/locales/zh-CN.js` after R1 identified those files as outside the declared list. Repository workflow requires the Coder to stop when a scope increase is needed rather than rewrite the Task plan. No user-approved plan amendment is recorded.
- **Impact:** The Task boundary is no longer an independent control. The locale additions may be appropriate, but their authorization cannot be created by the implementation under review.

### Medium - Evidence retains known limitations that contradict the R2 readiness claim

- **Files/lines:** `docs/review-evidence/UXS-004.md:72-77` versus `:49-60`.
- **Evidence:** The R2 section claims dashboard wiring and screenshots, while the unchanged Known Limitations section still says the dashboard is not wired and screenshots were not captured.
- **Impact:** The evidence is internally inconsistent and cannot serve as a reliable handoff record.

## Minimum Correction

1. Refresh the dashboard after realtime snapshots, after local calculations/input persistence, and after an active-month/year change. Add integration tests proving the rendered hero follows loaded data, an edit, and a month switch without changing legacy state or pending updates.
2. Recapture all six viewports in an authenticated/synthetic state that actually renders the dashboard. Record observed mobile first-screen priority, long Vietnamese, privacy mask, overflow, and desktop layout results in evidence.
3. Restore `TASK_PLAN.md` to the approved pre-UXS-004 content. Keep the bilingual locale files only after an explicit user-approved plan amendment; otherwise use the approved Task boundary and record the resulting blocker rather than self-amending it.
4. Correct the stale contradictory Known Limitations section once the above facts are true.
